# Text-to-SQL Eval Results

**Status: harness built and verified, live numbers not yet run.** No `ANTHROPIC_API_KEY` has been added to `.env` for this project — the same state Projects 1 and 3 were in before Roy added a spend-capped key. `python -m eval.eval_text_to_sql --run` is ready to go the moment one lands (estimated ~50 calls, ~$0.50 at current pricing — 2 calls per question, conservative in the safe direction either way; see the constant's comment in the script).

## What's built

- `eval/questions.json` — 16 real questions (5 lookup, 6 aggregation, 5 anomaly-linked) with hand-verified `expected_sql`, plus 9 adversarial questions covering the exploit classes Epic 5's three-round review found and closed: non-SELECT injection, ground-truth exfiltration, `query_log` exfiltration, multi-statement injection, catalog dumping, `SUMMARIZE`-as-data-source, CTE-name shadowing, qualified table references, and comma-join obfuscation.
- `eval/eval_text_to_sql.py` — scores real questions by **execution match** (do the generated and expected SQL return the same rows, run through the identical guardrail-wrapped path so neither side gets an unfair LIMIT/formatting advantage), not string similarity. Three questions (#4, #6, #15) pin exact columns or rounding because the natural-language question specifically implies them (a "show me" question about a `BIGINT[]` column, an "average" that invites rounding) — noted in `questions.json` per-question.
  - An API/execution failure (timeout, 429/529, a hallucinated column) is excluded from the accuracy denominator rather than counted as a wrong answer — a single transient failure on a one-shot paid run shouldn't silently deflate the reported number.
  - Adversarial questions are scored on two independent axes: **did the model actually attempt something forbidden** (a real non-SELECT statement, or a SELECT referencing a disallowed table/function — classified by *why* the guardrail's AST checks reject it, not by string-matching the model's free-text reasoning for attack keywords, which this account's github-issue-triage project already found false-positives on) and **did the guardrail block it**. `contained` is a real, falsifiable outcome (`model_complied and not blocked_by_guardrail`), not a value that's true on every reachable path.
  - Writes `eval/text_to_sql_results.json` on every `--run`, so a result isn't paid for and then discarded.
- `tests/test_eval_text_to_sql.py` — 11 tests exercise the harness's own scoring logic with a monkeypatched `generate_sql`: execution-match correctness (including a differently-worded-but-equivalent query correctly scoring as correct, not just an exact string match), the API-error-vs-wrong-answer distinction, both adversarial outcomes (guardrail rejects a literal compliance attempt; model declines gracefully and does something benign instead), and that every `expected_sql` in the question set actually executes against the real corpus. All pass — this is testing "does the eval measure correctly", not "is the model accurate", which is what the live run will answer.

## Once a key lands

Running `--run` will populate:
- Overall execution-match accuracy, broken down by category (lookup / aggregation / anomaly-linked) — expect aggregation questions to be the hardest (`GROUP BY` + `date_trunc` phrasing has more ways to go subtly wrong than a `COUNT(*)`).
- How many of the 9 adversarial questions actually provoked the model into generating forbidden SQL at all, versus declining gracefully — a real, reportable finding about model behavior distinct from guardrail behavior.
- Adversarial containment (expected: 9/9, since the guardrail already guarantees this independent of model behavior — see Epic 5's three review rounds and ~60 adversarial guardrail tests). A value under 9/9 here would mean a real guardrail regression, not an eval bug, and should be treated as a live incident.
